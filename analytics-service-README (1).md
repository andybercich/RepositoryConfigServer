# Analytics Service

## Overview

The Analytics Service is responsible for collecting, processing, and storing analytical data generated by the business operations handled by the other microservices.

It consumes business events from Kafka, processes order and stock movement information, and stores independent analytical records. This allows analytics data to remain decoupled from the transactional databases of the Order and Product services.

The service also provides monthly and annual reporting capabilities, including PDF generation and AI-powered business analysis using the Groq API through an OpenAI-compatible interface.

The Analytics Service does not receive business data directly through REST endpoints. Its analytical data is generated exclusively from Kafka events.

## Responsibilities

The main responsibilities of the Analytics Service are:

- Consume order-related events from Kafka.
- Consume stock movement events from Kafka.
- Transform business events into analytical records.
- Store independent order and product analytics data.
- Maintain monthly aggregated analytics.
- Prevent duplicated event processing.
- Generate monthly PDF reports.
- Generate AI-powered monthly reports.
- Generate annual AI-based reports.
- Generate analytical charts for reports.
- Store generated reports and their metadata.

## Kafka Event Consumption

The Analytics Service consumes four Kafka topics:

| Topic | Source | Purpose |
|---|---|---|
| `order-created-events` | Pedido Service | Processes newly created orders |
| `order-delete-events` | Pedido Service | Processes deleted orders |
| `order-updated-events` | Pedido Service | Processes updated orders |
| `stock-movement-events` | Product Service | Processes inventory movements |

Order-related events are handled by a dedicated consumer, while stock movement events are handled by a separate consumer.

All Analytics consumers use the following consumer group:

```text
analytics-group
```

There are no additional consumer groups used by the Analytics Service.

## Event Processing

The Analytics Service does not directly query the transactional databases of the other microservices to build its analytical records.

Instead, the required information is contained in the events published by the business services.

When an order event is received, the service processes it and creates or updates the corresponding analytical information.

Stock movement events are processed independently and generate product analytics records containing the inventory state before and after the movement.

This approach provides a separation between transactional business data and analytical data.

## Idempotency

The Analytics Service implements event idempotency using the `ProcessedEvent` entity.

For every incoming event:

1. The service checks whether the event ID has already been processed.
2. If the event ID already exists, the event is ignored.
3. If the event is new, it is processed normally.
4. The event ID is stored in `ProcessedEvent`.

`ProcessedEvent` is stored in the same database used by the Analytics Service.

This prevents duplicate Kafka events from generating duplicate analytical records.

```text
Kafka Event
     |
     v
Check ProcessedEvent
     |
     +---- Already exists ----> Ignore
     |
     +---- New event ---------> Process
                                  |
                                  v
                         Store analytics data
                                  |
                                  v
                         Store processed event
```

## Analytical Data Model

### OrderAnalytics

`OrderAnalytics` stores analytical information derived from order events.

| Field | Description |
|---|---|
| `orderId` | Identifier of the original order |
| `productId` | Identifier of the product |
| `productName` | Product name |
| `itemType` | Type of item involved in the order |
| `quantity` | Quantity involved in the order |
| `unitPrice` | Selling price per unit |
| `unitCost` | Cost per unit |
| `profit` | Profit generated by the item |
| `total` | Total value of the item |
| `createdAt` | Date and time of the analytical record |

### ProductAnalytics

`ProductAnalytics` stores analytical information derived from stock movement events.

| Field | Description |
|---|---|
| `productId` | Identifier of the product |
| `productName` | Product name |
| `category` | Product category |
| `movementType` | Type of inventory movement |
| `quantityChanged` | Quantity affected by the movement |
| `stockBefore` | Stock before the movement |
| `stockAfter` | Stock after the movement |
| `timestamp` | Date and time of the movement |

No additional analytical fields are currently required by these entities.

## Monthly Analytics

The service maintains monthly aggregated analytics through:

- `MonthlyAnalytics`
- `MonthlyProductAnalytics`

A `MonthlyAnalytics` record represents the aggregated information for a specific year and month.

`MonthlyProductAnalytics` stores the monthly summary for individual products.

The service prevents duplicate monthly records for the same year and month.

Monthly analytical data is generated incrementally from incoming events rather than recalculated from the original transactional services.

```text
Order Event
     |
     v
OrderAnalytics
     |
     v
MonthlyAnalytics
     |
     v
MonthlyProductAnalytics

Stock Movement Event
     |
     v
ProductAnalytics
     |
     v
Monthly Analytics
```

The Analytics Service generates PDF reports directly.

- iText for PDF document generation.
- JFreeChart for chart generation.

The current report generation process uses stored monthly analytical data to build the report.

### Available Charts

The service currently generates the following charts:

- Top Products
- Revenue and Profit by Week
- Stock Movements
- Top Profit Products
- Orders by Day
- Orders by Hour

The chart generation is handled by the service's chart component and the resulting charts are included in generated reports.

## AI Integration

The Analytics Service integrates with the Groq API through an OpenAI-compatible API.

The service prepares a `ReportDataDTO` containing the relevant analytical information and sends that data to the AI model for interpretation.

AI report generation is independent from PDF report generation.

### Monthly AI Analysis

Monthly AI reports return structured insights through `AIReportInsights`.

The response contains:

- Executive Summary
- Sales Insight
- Profitability Insight
- Stock Insight
- Product Insight
- Order Pattern Insight
- Recommendations

### Annual AI Analysis

Annual analysis is represented by `AIAnnualReportInsights`.

The response contains:

- Executive Summary
- Annual Performance
- Best and Worst Months
- Top Products
- Profitability Analysis
- Loss Analysis
- Recurring Products
- Sales vs. Profitability
- Trends
- Recommendations

The AI analysis is based on the analytical data generated by the service and is intended to provide business-oriented interpretation and recommendations rather than replace the underlying calculations.

### AI Failure Handling

If the Groq API is unavailable or the AI analysis cannot be generated, the service returns a controlled error response handled by the application's global exception handler.

## REST API

The Analytics Service exposes REST endpoints under:

```text
/analytics/reports
```

### Generate Monthly Report

```http
POST /analytics/reports/generate/monthly?year={year}&month={month}
```

Generates a monthly PDF report.

Parameters:

| Parameter | Type | Description |
|---|---|---|
| `year` | `int` | Report year |
| `month` | `int` | Report month |

Response:

```text
201 Created
```

The endpoint is protected by the `report` rate limiter.

### Generate Monthly AI Report

```http
POST /analytics/reports/generate/ia/monthly?year={year}&month={month}
```

Generates a monthly report using AI analysis.

Parameters:

| Parameter | Type | Description |
|---|---|---|
| `year` | `int` | Report year |
| `month` | `int` | Report month |

Response:

```text
201 Created
```

The endpoint is protected by the `aiReport` rate limiter.

### Generate Annual AI Report

```http
GET /analytics/reports/generate/ia/year?year={year}
```

Generates an annual AI-based report for the specified year.

Parameters:

| Parameter | Type | Description |
|---|---|---|
| `year` | `int` | Report year |

Response:

```text
200 OK
```

The generated file is returned as an attachment.

If the report cannot be found:

```text
404 Not Found
```

The endpoint is protected by the `aiReport` rate limiter.

### Get Generated Reports

```http
GET /analytics/reports
```

Returns the list of generated reports.

Response:

```text
200 OK
```

The endpoint is protected by the `report` rate limiter.

## Database

The Analytics Service uses MySQL as its persistence layer.

JPA/Hibernate is used for object-relational mapping.

The database contains the analytical and reporting data managed by the service, including:

- `OrderAnalytics`
- `ProductAnalytics`
- `MonthlyAnalytics`
- `MonthlyProductAnalytics`
- `ProcessedEvent`
- Generated report information

Example database configuration:

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/analytics
spring.datasource.username=root
spring.datasource.password=${DB_PASSWORD}
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
```

The database credentials should be provided through environment-specific configuration rather than committed credentials.

## Configuration

The service requires configuration for JWT and AI integration.

Relevant properties include:

```properties
spring.ai.openai.api-key=${API_IA}

jwt.secret=${JWT_SECRET}
jwt.expiration=${JWT_EXPIRATION:3600000}
```

The service also requires the standard database and Kafka configuration used by the application environment.

Sensitive values such as API keys, JWT secrets, and database credentials should be supplied through environment variables.

## Security

The Analytics Service uses JWT-related configuration as part of the application's security model.

The service is intended to operate behind the API Gateway in the complete microservices architecture.

When accessed through the API Gateway, requests to:

```text
/analytics/**
```

are routed to the Analytics Service.

The API Gateway also applies request rate limiting to Analytics endpoints using Redis.

The gateway configuration uses:

```text
replenishRate: 1
burstCapacity: 20
```

Individual report operations also use application-level rate limiters such as `report` and `aiReport`.

## Observability

The Analytics Service participates in the project's distributed tracing and structured logging approach.

Requests and operations can be correlated through the `X-Trace-Id` mechanism, while application logs use structured JSON / Logstash-compatible formatting.
